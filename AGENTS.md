# Инструкции для ИИ-агента

Ты дописываешь веб-приложение на React. Язык интерфейса, текстов для людей и общения — русский.

## С кем ты работаешь

Человек, скорее всего, не программист: он описывает, что хочет получить, а код пишешь ты.

- Объясняй простыми словами, что сделал и что изменилось на экране. Не проси человека править код или читать ошибки сборки.
- Проверки запускай сам и сам чини то, что они нашли. Работа закончена, когда `yarn verify` проходит.
- Нужно что-то от бэкенда, чего нет в `api/backend-schema.yaml`, — скажи об этом прямо: фронтенд не может это выдумать.

### Сначала уточни задачу

Просьбы обычно короткие: «сделай страницу заказов». Прежде чем писать новую страницу или заметную функцию, выясни, что человек на самом деле хочет увидеть.

- Факты выясняй сам: что уже есть в коде, что умеет бэкенд. Человека спрашивай только о том, что решает он.
- Спрашивай о поведении: что человек видит на экране, что вводит, что происходит после нажатия, что показать, если данных нет или случилась ошибка. Библиотеки, папки и устройство кода выбирай сам.
- Вопросы — по одному. К каждому предлагай свой вариант ответа, чтобы человеку хватило сказать «да».
- Обычно хватает двух-пяти вопросов. Мелкую правку, опечатку или понятную просьбу делай сразу, без вопросов.
- Перед тем как писать код, перескажи в двух-трёх предложениях, что получится, и дождись согласия.

### Не раздувай

- Делай то, о чём просили. Настройки, функции и заделы «на будущее» без просьбы не добавляй. Если они кажутся полезными, предложи их одной строкой в конце.
- Сначала ищи готовое: компонент в `@/shared/ui`, функцию в проекте, возможность уже установленной библиотеки. Новую зависимость ставь, только если без неё выйдет заметно больше кода.
- Выбирай самое маленькое изменение, которое решает задачу целиком, вместе с тестом и правками там, где изменение что-то задело.
- Если что-то осталось непроверенным, в конце ответа скажи простыми словами, что именно и чем это грозит.

## Что это

Приложение создано из шаблона `react-web` панели paas. Панель собирает его в образ и выкатывает на сервер рядом с бэкендом проекта. Сейчас в нём одна страница-заглушка `src/pages/home`: замени её первой настоящей страницей.

Стек: React 19, TypeScript, Vite, React Router, TanStack Query, Tailwind CSS 4, компоненты shadcn/ui, React Hook Form и Zod, Vitest и Testing Library.

## Договор с панелью — не нарушай

Панель выкатывает приложение, не читая код, по этим соглашениям. Если их сломать, сборка или выкатка упадёт.

- **`.paas/template` и `CHANGELOG.md` — метки шаблона.** `.paas/template` хранит версию шаблона, из которой код приложения; её ставит панель, и по ней она предлагает обновление PR-ом. Не правь её руками. `CHANGELOG.md` — что нового в версиях шаблона.
- **`paas.toml` — настройки приложения на сервере.** Число копий и размер задаёт только этот файл; панель читает его при раскатке. Неизвестный ключ — ошибка: сборка проверяет файл и с ошибкой не соберёт версию. `name` не меняй: он равен имени репозитория. Пояснения — комментарии в самом файле.
- **Не меняй `Dockerfile`, `Caddyfile` и `.github/workflows/release.yml`.** По ним каждый пуш в `main` собирает образ `ghcr.io/<организация>/<репо>/web` с тегом версии.
- **Запросы к бэкенду — только по относительным путям `/api/...`.** В образе всё под `/api/` пересылается бэкенду проекта; адрес бэкенда панель передаёт при запуске. Не вшивай адрес бэкенда в код и не заводи для него переменные `VITE_*`: они попадают в сборку, и смена адреса потребовала бы новой версии.
- **Адреса страниц не должны начинаться с `/api` и быть `/health`.** `/health` отвечает панели, что приложение запущено.
- **Сборка — `yarn build` в `dist/`.** Не меняй команду и папку: образ берёт файлы оттуда.
- **Секретов во фронтенде нет:** всё, что попало в сборку, видно любому посетителю. Ключи внешних сервисов держит бэкенд.

## Куда класть код

Код разложен по Feature-Sliced Design 2.1. Подробные правила — в скиле `feature-sliced-design`; загрузи его, когда решаешь, где должен лежать код.

Слоёв три: `src/app` (запуск, маршруты) → `src/pages` (страницы) → `src/shared` (общее без предметной логики). Импорт идёт только вниз, через `index.ts`, с алиасом `@/`.

- Всё, что нужно одной странице, лежит в её папке: `pages/<страница>/ui`, `api`, `model`.
- Слои `features` и `entities` не заводи заранее. Они появляются, когда один и тот же код с предметными правилами реально нужен нескольким страницам.
- Структуру проверяет линтер Steiger в `yarn lint`: если он ругается, исправь расположение кода, а не отключай правило.

### Как добавить страницу

1. Создай `src/pages/<страница>/ui/<страница>-page.tsx` и `src/pages/<страница>/index.ts` с экспортом компонента.
2. Добавь маршрут в `src/app/router/index.tsx`.
3. Запросы страницы положи в `src/pages/<страница>/api/`, схему формы — в `src/pages/<страница>/model/`.
4. Напиши тест рядом с кодом (`*.test.tsx`) и выполни `yarn verify`.

## Правила кода

- Данные бэкенда — только через TanStack Query и `apiRequest` из `@/shared/api`. Функцию запроса и ключ запроса держи рядом: в `api` страницы, а когда запрос нужен нескольким страницам — в `src/shared/api`. После изменения данных вызывай `invalidateQueries` по этому ключу.
- Ошибка бэкенда приходит как `ApiError` с текстом для человека. Показывай его как есть.
- Типы запросов и ответов бери из `ApiSchemas` (`@/shared/api`), не описывай их руками.
- Формы — React Hook Form и схема Zod с теми же ограничениями, что проверяет бэкенд. Поля собирай из `Field`, `FieldLabel`, `FieldError` из `@/shared/ui` и `Controller` из React Hook Form.
- Интерфейс собирай из `@/shared/ui`. Там уже есть Alert, Button, Card, Dialog, DropdownMenu, Field, Input, Label, Select, Separator, Skeleton, Spinner, PageLoader, Table, Textarea. Нужного нет — `npx shadcn@latest add <компонент>`, затем добавь экспорт в `src/shared/ui/index.ts` и выполни `yarn format`. Как выбирать и сочетать компоненты — в скиле `shadcn`.
- Уведомления — `toast` из пакета `sonner`. `Toaster` уже подключён в `src/app/App.tsx`.
- Тесты — Vitest и Testing Library. Запросы подменяй через `vi.stubGlobal('fetch', ...)`; заготовка — `src/app/App.test.tsx`.
- Комментарий — одна строка и объясняет «почему».

## Связь с бэкендом

Типы клиента API собираются из `api/backend-schema.yaml` — копии контракта бэкенда (`api/schema.yaml` в его репозитории). Бэкенд поменял контракт — скопируй его файл сюда целиком и выполни `yarn api:generate`. Результат в `src/shared/api/generated/` закоммить: CI проверяет, что он свежий. Руками этот каталог не правь.

## Команды

- `cp .env.example .env.local && yarn install && yarn dev` — разработка на http://localhost:5173; `/api` уходит на `BACKEND_URL` из `.env.local`.
- `yarn verify` — всё, что проверяет CI: линтер, форматирование, тесты, сборка. Не `yarn check`: это встроенная команда Yarn, она проверяет другое.
- `yarn format` — исправить форматирование.
- `yarn api:generate` — типы клиента API после правки `api/backend-schema.yaml`.
